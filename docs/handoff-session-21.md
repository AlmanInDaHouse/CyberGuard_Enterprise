## SPEC-011 (incident severity aggregation) — delivery declaration

Forensic step 2 (incident-level severity) is **delivered in full**.

**Delivered:**

- **The column — `incidents.severity_id` (SPEC-011 §Data contracts §1).** `smallint NOT NULL`, OCSF ordinal **0–6**, added by **migration `0006_incident_severity.ts`** with `CONSTRAINT incidents_severity_range CHECK (severity_id BETWEEN 0 AND 6)` — a byte-mirror of `alerts_severity_range` (`0002_alerts.ts:50`). The migration is **three steps in order**: add nullable → backfill `MAX(alerts.severity_id over alert_ids)` → `SET NOT NULL` + range CHECK. It is **transactional** by the Kysely `Migrator`'s per-run transaction (`migrator.js` — Postgres `supportsTransactionalDdl`), mirroring the `0004` add→backfill→NOT-NULL precedent; the `SET NOT NULL` **after** the backfill is load-bearing (an out-of-order migration would reject the freshly-NULL rows).
- **The aggregation — MAX, recomputed in the upsert (SPEC-011 §Operational §3).** `services/ingest/src/detect/incidents.ts` adds, as one unit, `severity_id` to the INSERT column list + its `VALUES` parameter + `severity_id = GREATEST(incidents.severity_id, excluded.severity_id)` in the `ON CONFLICT … DO UPDATE SET` (alongside the existing `alert_ids` CASE and `updated_at`). A new correlated alert can only **raise** an incident's severity, never lower it. `IncidentGroupingInput.severityId: number` (required, non-nullable) is sourced from `RuleMatch.severityId` at the detection call site (`detect/index.ts`) — always present (`engine.ts` parses `cg.severity_id` as `z.number().int().min(0).max(6)`), so `GREATEST` never sees NULL.
- **The re-worded triage-preservation invariant (`detect/incidents.ts` docstring).** The SPEC-007 clause *"the SET touches ONLY alert_ids and updated_at"* became false once `severity_id` joined the SET, so it is re-worded into **two field classes**: **machine-recomputed on every correlated alert** (`alert_ids` accumulates set-semantically; `severity_id` rises to the running MAX) vs **preserved triage-state** (`status` / `assigned_to` / `activity_id` / `cg_mitre` / `title` — never touched by the upsert). The substantive promise is unchanged: a new correlated alert never resets a human's triage. `cg_mitre` stays **frozen-at-creation** (the deliberate asymmetry: severity recomputes, `cg_mitre` does not).
- **The read-model (SPEC-011 §Data contracts §3).** `severity_id` added to `IncidentListItem` + `IncidentDetail` (`services/api/src/read/types.ts`); projected by `listIncidents` + `getIncidentDetail` (`services/api/src/read/queries.ts`); mirrored additively into the dashboard wire-contract (`dashboard/src/lib/api/types.ts`). The read routes declare **no Fastify response schema** (`read/routes.ts`), so the projected field reaches the JSON unstripped. Purely additive — no consumer assumed an incident severity before this SPEC (the S20-era audit confirmed it absent everywhere).
- **4 acceptance criteria, green:**
  - **AC-001** (the MAX marquee — commutativity): two alerts in one window, `low→high` and `high→low`, both collapse to one incident at `high` (`services/ingest/test/incident-severity-ac-001-max.test.ts`).
  - **AC-002** (triage preserved while severity escalates — **extends** `incident_ac_004`): after an analyst moves the incident to `investigating`/`analyst-x`, a higher-severity alert raises `severity_id` to the MAX while the three original triage assertions survive (`services/ingest/test/incident-ac-004-triage-preservation.test.ts`).
  - **AC-003** (read-model projects it): `GET /v1/incidents` (list) and `GET /v1/incidents/:id` (detail) both return `severity_id = MAX(member alerts)` (`services/api/test/incident-severity-ac-003-readmodel.test.ts`).
  - **AC-004** (backfill correctness + ordering): against a **throwaway database** migrated to `0005` (no severity column), seed an incident over mixed-severity alerts, then `migrateToLatest()` applies `0006` and backfills `severity_id` to the MAX (`services/ingest/test/incident-severity-ac-004-backfill.test.ts`).
- **SPEC-010 `:32` realised by-scope.** SPEC-011 delivers SPEC-010's deferred-with-destination *"Severity / score aggregation per incident"* (`SPEC-010:32`). Catalog edges recorded: `SPEC-011 → SPEC-010` (realises `:32`), `SPEC-011 → SPEC-007` (extends the upsert + re-words the invariant), `SPEC-011 → SPEC-009` (adds `severity_id` to the read-models).

**Ratified design decisions (Manuel's diff gate):**

- **Scale = OCSF ordinal 0–6**, identical to `alerts.severity_id` — **closes the schema-vs-wire divergence**: the canonical wire example already carried `"severity_id": 5` on an incident (`schemas/cges/v0.1/examples/06_incident_grouped.json:11`) though the JSON-Schema class omitted it (`additionalProperties: true` permitted it). **Not** the blueprint's inconsistent `incident.severity >= 8` playbook scale (`blueprint.md:423`) — reconciling that is out of scope.
- **Semantics = unconditional MAX.** The blueprint prescribes **no** derivation semantics (it lists severity as a display attribute, `blueprint.md:556`; the incident phase is *"groups related alerts"*, `:390`) — so MAX is a ratified SOC-posture choice (an incident is as severe as its worst alert), recomputed (not frozen) because severity tracks the running evidence.
- **Backfill is fail-loud, no COALESCE.** A dangling `alert_ids` (no matching `alerts` row) → `MAX = NULL` → `SET NOT NULL` fails → the whole migration rolls back, **surfacing corruption rather than masking it** with an invented severity. In a faithful DB every `alert_ids` entry references a real alert (created together, Convention #12).

## Procedural notes — Session 21

- **Marquee stale-binary precondition — institutionalized into CLAUDE.md this session (the headline note).** `detect_ac_001` went red with `cges_events` count 0 / `eventsEvaluated` 0 — a **silent symptom** (clean exit, no panic) indistinguishable at a glance from "not elevated" or a dirty watermark. Root cause: a **week-old `cg-agent.exe` (built 2026-05-29)**; rebuilding (`cargo build --release -p cg-agent`) flipped it green (captured events 0 → 51, alert 0 → 1). It was a **costly red herring (~1 h of diagnosis)** that looked like a SPEC-011 regression but never was — `cges_events` emission is agent-Rust → ingest, **upstream** of all detection/severity code (the diff is TypeScript-only). The fix: a **precondition** added to CLAUDE.md §"Developer-local SPEC-006 marquee validation" — always rebuild + verify the `.exe` timestamp before the marquee, **unconditionally** (Convention #10 conditioned it on "agent source changed"; the binary can be stale from a prior session even when the current one never touched `agent/`). The diagnosis method that proved it upstream: test-only `[marquee-diag]` instrumentation (reverted before landing) logging `getCgesEvents`/`getWatermark` + the `runDetectionCycle` return; plus the static evidence (separate `pg.Pool` per upsert → no shared txn; failure at marquee `:77` not `:74` → the cycle completed without throwing).
- **The READ-ONLY audit → diff-gate → atomic-land flow, used again.** S21 reused S20's flow for a bounded increment with an Accepted-doc gate. Still **not** a license to skip harness-first RED for a new phase or public surface — SPEC-011 is additive within existing surfaces.
- **Throwaway-DB migration-backfill test pattern** (see Debts/deferred) — `migrateTo(<name>)` + a per-test database is how to test a backfill faithfully when the shared suite DB is already at `latest`.
- **Node v24 `-e` type-strips as TypeScript.** A `node -e '…'` one-liner with template literals + a ternary was parsed as TS and threw `SyntaxError` every poll iteration (the first CI-poll loop produced no status for 10 min). Use a `.cjs` file for JSON parsing in CI-monitoring scripts, not `node -e`.
- **`markdownlint` local-vs-CI version skew (carried).** Local `markdownlint v0.40.0` flags `MD060/table-column-style` on pre-existing table separators that the CI action (`markdownlint-cli2-action@v16`) does not (main is green). When the local linter reports errors only on lines you did not touch, verify against `HEAD` before "fixing".
- **`gh` CLI is not installed in the agent environment.** CI monitoring used the REST API fallback (token via `git credential fill`, never logged) per CLAUDE.md §CI monitoring fallback.
