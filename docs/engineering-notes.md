# Engineering notes

Session-level engineering lessons. Not ADRs (no architectural decision), not SPECs (no feature). Working memory: patterns that accelerate similar decisions later. If a pattern recurs, promote it to an ADR.

## Session 5 (2026-05-20)

- **Test API exposure trade-off.** If a test requires exposing something dubious to the public API (e.g. internal logger primitives for AC-009 testability), restructure the test rather than the API. Bloating public surface for test convenience accumulates faster than expected.
- **chrono dependency trade-off.** `chrono` is heavy but the alternative (manual ISO 8601 with days-from-epoch) was 30+ lines and edge-case-prone. For RFC 3339 timestamps in the agent, `chrono` is the right call.

## Session 10 (2026-05-23)

- **Follow-ups are co-located with the document that generates them.** A spike's follow-ups live at the bottom of the spike note; an ADR's follow-ups live at the bottom of the ADR; an amendment's follow-ups live with the amendment. No central `docs/follow-ups.md` index is created proactively — that would be premature abstraction. If dispersion later makes auditing hard, an index gets created **then**, populated from the existing in-place sections. The rationale is that a follow-up is most useful when read next to the evidence that justified it; separating them loses signal.
- **ADR Deciders field — three-role convention formalised.** Every ADR header uses `- Deciders: Manuel (project owner), Claude (architecture advisor), Claude Code (implementation)` verbatim. ADRs 0001–0008 already use this form by consistent copy; this note promotes it from accidental pattern to explicit precedent so future ADRs adopt it by reference, not by copy.
- **Cross-reference convention — provenance points to the cause, not the effect.** When an amendment closes a prior drift, the rewrite-side bullet cites the drift's **original declaration** (the cause), not the amendment (the effect). A future reader follows the arrow to the cause, sees the drift, and finds the amendment as the closure; reverse arrows force backwards reconstruction. Adopted while writing ADR-0004's 2026-05-23 amendment part (b), which closed SPEC-003 §Drift D3 in ADR-0004's prose.
- **Internal cross-check for multi-mention claims.** Any document where a load-bearing claim appears in more than one place (e.g. ClickHouse partitioning summarised in Context AND specified in Decision) needs an internal-consistency pass before submission, not only when amending a ratified file. Surfaced while reviewing the ADR-0009 draft, where a Context-section paraphrase of ADR-0003's partitioning contradicted the Decision-section spec.
- **Audit cross-references on reserved-ADR repurposing.** When a reserved ADR number is ratified for a new topic (e.g. ADR-0008 was reserved for "contract generation tooling" and ratified as "ETW crate selection"), sweep the repo for cross-references that were written under the old reservation. Lexical audit scoped to an amendment's immediate terms cannot catch these — they need a separate sweep. Surfaced when ADR-0004's §Consequences > Neutral still attributed API-versioning to "ADR-0008 (contract generation tooling)" after ADR-0008's ratification this session.
- **Dependency-graph edge convention — "amends in part" vs "supersedes".** When an ADR amends another ADR in-place (via `## Amendment <date>:` section, target ADR stays `Accepted`), the dependency-graph edge in [docs/adr/README.md](adr/README.md) is labelled "amends in part," not "supersedes." Supersession is reserved for cases where the target ADR's status flips to `Superseded`. The distinction matters: "amends in part" preserves the target's accepted-status authority; "supersedes" retires it. Adopted with ADR-0009's edge to ADR-0004.
- **Dep-graph edges capture constraint-bearing relationships only.** Non-constraining but topic-relevant relationships live as bullets in the ADR (typically §Consequences > Neutral or an inline cross-reference), not as edges. Do not invent edges to document absences — an edge labelled "non-constraining cross-reference" is incoherent. Absence of edge **plus** an explicit bullet explaining the absence is more informative than an edge with an apologetic annotation. Adopted while drafting ADR-0010's relationship to ADR-0004 (DPAPI privilege-orthogonality: topic-relevant, non-constraining; documented as a Neutral bullet, no edge).
- **Spike notes are point-in-time records, not living documents.** Their text is anchored to the date in the filename; forward-references that become stale after the spike's date are NOT edited retroactively. Erratas (typos, factual misstatements about the moment of writing) are editable; semantic updates (forward-pointers fulfilled, decisions later changed) are not — those would be documentary revisionism. This distinguishes spike notes from ADRs in the doc taxonomy: ADRs speak in the present (amended in-place when their content changes); spike notes speak in a date-anchored past. Adopted when ADR-0010's ratification surfaced "ADR-0010 (forthcoming)" in [docs/spikes/2026-05-23-etw-process-events.md](spikes/2026-05-23-etw-process-events.md) — kept unchanged because the statement was true on 2026-05-23 when the spike was written.
- **Bidirectional cross-reference audit on amendment.** When document X is amended, audit cross-references **to** X from other documents in the same session — they may need provenance updates. This is the inverse direction of the "provenance to cause" and "audit on reserved-ADR repurposing" conventions, which cover cross-references **from** the amended document. Together, the three conventions form a bidirectional matrix: amendments propagate both within X (handled by the in-document lexical audit per the Session 9 lesson) and across documents that cite X (handled by this convention). Adopted when SPEC-003's amendment audit surfaced three provenance citations to ADR-0004 sections that this session's ADR-0004 amendment had already changed.

  **Procedural footnote.** Cross-references detected **during drafting** (not during the formal audit pass) should be surfaced explicitly in the draft for chat approval before being silently applied, even when the correction is factually obvious. The audit pass is the moment of accountable scope-setting; corrections found later need an explicit retroactive scope-extension, not silent inclusion. Adopted after a *"Go ingest service"* → *"TypeScript ingest service"* correction was found during SPEC-003's amendment drafting (Session 10) without surfacing in the audit pass — the correction was kept (documentary integrity beats procedural integrity when the substance is non-controversial) and part (c) was extended in chat-approved form, but the procedural pattern is recorded so future audits surface the find at audit-time, not drafting-time.

## Session 16 (2026-05-29)

Phase 4 (ETW capture investigation) opened and closed in one session. The marquee AC-001 went from RED (zero events reaching ClickHouse) to 8/8 GREEN developer-local across eight distinct failure layers, each surfaced and resolved sequentially. Four procedural notes; two are candidates for convention promotion (marked).

1. **Release binary gotcha (candidate for convention).** The SPEC-005 marquee launches a pre-compiled agent binary via `agentBinaryPath()` (`target/{release,debug}/cg-agent.exe`). It does NOT compile the agent as part of the test. Therefore: every edit to agent source requires `cargo build --release --bin cg-agent` before running the marquee — `cargo check` and `cargo clippy` validate source but do not regenerate the .exe. This cost a full Phase 4 iteration: the marquee ran three times against a binary that predated the keyword fix, producing identical failures that appeared to falsify the fix. Verification protocol: confirm the .exe timestamp is posterior to the edit (`Get-Item ...release\cg-agent.exe | Select LastWriteTime`), and look for the expected new log line in the agent's stdout before interpreting test results. *Convention candidate: any session that modifies agent code and validates via a pre-compiled-binary test MUST rebuild and verify the .exe timestamp before the test run.* **[PROMOTED in Session 18 → Convention #10.]**

2. **cargo fmt in the pre-commit gate (candidate for convention).** `cargo check` + `cargo clippy` do not validate formatting. CI runs `cargo fmt --check` and fails if it differs. Including `cargo fmt --all` (or `--check`) in the local pre-commit gate prevents a follow-up formatting commit on every push. Occurred once in Phase 4 (`3581b60`, fmt fix on `events_lost_impl.rs`). *Convention candidate: the local agent gate is `cargo check` + `cargo clippy -D warnings` + `cargo fmt --all --check`, not just check+clippy.* **[PROMOTED in Session 18 → Convention #11; codified in CLAUDE.md §"Local pre-commit gate".]**

3. **Eight-layer ETW capture chain — diagnostic archaeology.** The Session 15 handoff listed three hypotheses for the ETW dispatch-callback silence (H1 KernelTrace vs UserTrace, H2 privilege, H3 enable flags). All three were incorrect or secondary. The actual chain of root causes, in discovery order: **(a)** ProcessTrace never invoked (`start()` does not call ProcessTrace; `start_and_process()` or manual `process_from_handle()` required — identified by reading ferrisetw 1.2 source); **(b)** ETW privilege (`E_ACCESSDENIED` on `StartTraceW` from non-elevated context — resolved by running from elevated shell per ADR-0010 §Decision part 1); **(c)** zombie ETW session (`ERROR_ALREADY_EXISTS` — resolved by `reclaim_zombie()` via `ControlTraceW(STOP)`, matching the Phase 0 spike's `stop_zombie()` pattern); **(d)** thread topology (`start_and_process()` + `park()` separated the session-owner thread from the ProcessTrace pump thread; collapsing to `start()` + `process_from_handle()` on one dedicated thread resolved the dispatch gap — ferrisetw documents this as the "most powerful option"); **(e)** `MatchAnyKeyword=0` ambiguity (does not reliably deliver `WINEVENT_KEYWORD_PROCESS` events on this Windows 11 build; explicit `.any(WINEVENT_KEYWORD_PROCESS)` required — identified by querying the provider manifest via `wevtutil`); **(f)** ETW property names (`ImageFileName` → `ImageName`, `ExitStatus` → `ExitCode` — provider manifest is authoritative, not the code's assumptions); **(g)** IEEE 754 precision loss on the signed envelope wire (u64 nanos > 2^53; `JSON.parse` rounds; JCS canonical form diverges; Ed25519 signature fails with `bad_signature` 401 — confirmed 8/8 rejected; resolved by string-encoding nanos); **(h)** unstable `process.uid` across Launch/Terminate (ETW Terminate EventRecord carries termination timestamp, not creation timestamp; `CreatedTimeCache` feeds the uid on Terminate — falsified the premise in SPEC-005 §Operational §2 and ADR-0011 §6). The method that worked across all eight layers: the Phase 0 spike was the empirical source of truth — the documented API usage in [docs/spikes/2026-05-23-etw-process-events.md](spikes/2026-05-23-etw-process-events.md) (permanent, in-repo) and the executable spike code at `c:\tmp\etw-spike\` (local, ephemeral). No fix was applied without verifying the spike's actual API usage or the crate/provider source first.

4. **Gate-before-marquee pattern.** Reviewing each fix's diff and verifying API/type correctness against the ferrisetw source or provider manifest BEFORE spending an elevated marquee run (~1.5 min + Docker Desktop + UAC) saved multiple iterations. The expensive feedback loop (edit → rebuild → elevate → run marquee → diagnose) was front-loaded with cheap verification (read source → propose diff → gate → approve → rebuild → run). Documentary — not promoted to convention status (project-specific workflow shaped by the elevated-shell constraint of ADR-0010 §Decision part 1).

## Session 17 (2026-05-31)

Phase 5 (Detection MVP, Route A) opened and closed in one session: the detection slice (ClickHouse `cges_events` → normalize → Sigma rule → renormalized score → Postgres `alerts`) went from harness-first RED to all six `detect_ac` green (002–006 in CI, 001 validated developer-local with a real ETW capture). Four procedural notes; two are candidates for convention promotion (marked).

1. **ClickHouse SELECT-alias column shadow (documentary).** The 5b read-model query projected `toString(time) AS time`, reusing the source column's name for the formatted string. ClickHouse then resolved the bare `time` in the same query's `WHERE time > {watermark:String}` to the aliased String projection, not the underlying `DateTime64` column → `No operation greater between String and DateTime64`. Three successive attempts to fix the *comparison* failed identically because the comparison was never the bug — the alias was shadowing the column for the rest of the query scope. Fix: project to a distinct name (`AS event_time`) and leave the bare column available for `WHERE`/`ORDER BY`. Lesson: in ClickHouse a SELECT alias that reuses a source column's name shadows that column for `WHERE`/`ORDER BY` in the same statement; name projections distinctly. The repeated identical failure was itself the tell that the fix target was wrong, not the fix.

2. **IEEE-754 tail into a fixed-precision column (documentary).** The 5d scorer renormalizes the weighted sum over active-source weights; for the rule-only path `(0.6 · 0.9) / 0.6` evaluates in IEEE-754 double to `0.9000000000000001`, not `0.9`. `detect_ac_006` asserts `toBe(0.9)`, and the `alerts.final_score` column is `numeric(4,3)`. Fix: round to the column's precision at the source (`Math.round(x * 1000) / 1000`), which both matches storage and erases the float tail. Same IEEE-754 class as Phase 4's string-nanos wire fix (§Session 16 note 3g), surfacing one layer over (scoring arithmetic, not the signed-envelope wire). Lesson: any computed numeric destined for a fixed-precision column should be rounded to that precision at the source, never relied upon to compare exactly as a raw float.

3. **Integrity-constraint failure in a synthetic test → fix the test, not the schema (candidate for convention).** When 5e wired the real `runDetectionCycle`, `detect_ac_003/004/005` failed with `violates foreign key constraint "alerts_agent_id_fkey"`: they fabricate `cges_events` rows directly (ClickHouse `cges_events` has no FK to `agents`), so the alert the cycle persists references an `agent_id` with no `agents` row. Two options surfaced — (a) enroll the synthetic agent before the cycle (`enrollTestAgent`), or (b) drop/relax the FK. (b) was rejected: the FK failing was the schema *doing its job* — in production every agent emitting events is enrolled (it cannot POST without an mTLS identity), so an alert always references an enrolled agent. The test was unfaithful, the schema was right. `enrollTestAgent` made the test reflect the production precondition; the FK stayed; the assertions were untouched. *Convention candidate: a synthetic test that trips a DB integrity constraint is fixed by satisfying the production precondition the constraint encodes (e.g. enrolling the agent), never by weakening the constraint — unless the constraint itself is demonstrably wrong. Weakening the schema to green a test hides the very invariant the test should respect.* **[PROMOTED in Session 18 → Convention #12.]**

4. **Known CI debt co-located with the SHA it explains (candidate for convention).** Phase 5's harness-first RED opened the `ts-ci` debt row in the *same* commit that turned the workflow red (`24e0e4a`), narrowed it when `detect_ac_006` closed (`fcc82f2`), and removed it in the *same* commit that turned the workflow green (`34aa436`). This rule was codified into CLAUDE.md mid-phase (§"Harness-first red phases and debt co-locality") as the explicit lesson of Sessions 6–7: splitting the debt declaration from the red-turning commit — e.g. landing the debt row in a docs-only commit that dodges the path filter, then landing the red tests separately — satisfies the letter but violates the spirit, because anyone inspecting the red SHA must see both the failing run and its accepted reason together. Phase 5 exercised the full open→narrow→close lifecycle cleanly. The rule is already binding in CLAUDE.md; the candidacy is to elevate it to a numbered convention in this catalog. *Convention candidate: promote the CLAUDE.md §"Harness-first red phases and debt co-locality" rule to a numbered convention — debt declaration co-located with the red-turning SHA, debt removal co-located with the green-turning SHA, no path-filter splitting.* **[PROMOTED in Session 18 → Convention #13; pointer to CLAUDE.md §"Harness-first red phases and debt co-locality".]**

### Phase 6 = C (read-slice) — api↔ingest schema-sharing debt (architecture, named)

SPEC-009's read-API (`services/api`) reads `incidents`/`alerts`/`agents`, tables **owned by the ingest service's migrations**. Because `services/api` and `services/ingest` are independent pnpm packages (no workspace) and api's migration runner (Option A, SPEC-008 §7) applies only its own tables, the read-API test harness can neither run ingest's runner (its ClickHouse bootstrap is not separable from `runMigrations`, `services/ingest/src/db/migrate.ts:83/:86`) nor cross-import ingest's migrations (static → `rootDir` TS6059; dynamic → `kysely` unresolvable in the `check-api` job, which installs only api's deps). The SPEC-009 read-API RED gate therefore materialises the read-target tables with a **test-only DDL mirror** (`services/api/test/helpers/read-schema.ts`, option (c)), scoped to the columns the read-API consumes, with a drift in a read column caught by a read AC at GREEN. **Architecture debt → option (b)** (distinct from CI debt): replace the mirror with a shared schema package or a pnpm-workspace cross-import when the shared api↔ingest surface grows. **Trigger:** a second ingest table the mirror does not cover, or the first un-caught drift. This is the project's first cross-service schema-read; it surfaced the separate-package boundary as the real constraint.

### Phase 6 = C — pnpm-workspace introduced (realises ADR-0001 at the tooling level)

To unblock the dashboard's data-access test (PART 2/2) against the real read-API in-process — and to enable retiring the (b) schema-sharing debt above — a `pnpm-workspace.yaml` was introduced (`packages: ["services/*"]`; `dashboard` added when it lands), realising [ADR-0001](adr/0001-monorepo-layout.md) at the tooling level (no new ADR — it implements the monorepo decision, it does not change it). Consequences surfaced and handled: (1) the workspace uses ONE root lockfile (`pnpm-lock.yaml`) — the per-package lockfiles were removed; (2) `pnpm.onlyBuiltDependencies` (biome, esbuild) must live at the workspace root, as pnpm ignores per-package copies — moved to the root `package.json` (per-package copies removed), else biome/esbuild are not built and lint/test break; (3) no effective dependency-version change (ingest/api shared pins were already aligned — verified); (4) `pnpm install --frozen-lockfile` run per-package in CI still works (it installs the whole workspace from the root lockfile — verified), so `ts-ci` needed only its path filter widened to the root workspace files. The cross-package wall that forced the read-API materialisation to option (c) is now removable: **the (b) debt is retirable in a dedicated follow-up gate** (the read-API test-only schema mirror → a faithful in-workspace import of the ingest migrations); it is intentionally NOT retired in this workspace-introduction commit (that touches the read-API's 31 tests and merits its own verification).

### Phase 6 = C — (b) schema-sharing debt RETIRED (faithful in-workspace ingest-migration import)

The (b) architecture debt declared in §"api↔ingest schema-sharing debt" above is **RETIRED**. The read-API test harness no longer materialises the read-target tables from a test-only DDL mirror; it now applies **ingest's REAL Postgres migrations in-workspace** (`services/api/test/helpers/read-schema.ts`, `applyReadSchema`). Mechanism + the two walls re-verified under the workspace:

1. **ClickHouse wall (re-verified, avoided faithfully).** ingest's `runMigrations` couples a ClickHouse bootstrap (`services/ingest/src/db/migrate.ts:83` → private `bootstrapClickHouse` `:86`), so it is NOT called. ### Phase 6 = C — dashboard scaffold + harness-first RED (the project's first UI; SPEC-009 PART 2/2)

The minimal SOC dashboard (Next.js 15 App Router + Tailwind + TanStack Query, `dashboard/`) landed as scaffold + RED harness, the last RED of slice C. Non-obvious decisions future UI sessions inherit:

1. **Two import idioms coexist in the workspace — extensionless for Next, `.js` for NodeNext.** The dashboard's `tsconfig` is Next's (`moduleResolution: "bundler"`, `jsx: "preserve"`), so its OWN source imports are **extensionless** (`@/components/...`). `services/api`/`services/ingest` stay NodeNext (explicit `.js`). Webpack does NOT rewrite `.js`→`.tsx` for the `@/*` alias the way tsc-bundler does, so a `.js` suffix on a dashboard-internal import breaks `next build` (`Module not found`) while passing `tsc` — a silent mismatch caught only by building.
2. **`force-dynamic` keeps `next build` GREEN while the data-access logic is absent.** The `/incidents` + `/incidents/[id]` RSC pages read `cookies()` and call the data-access layer (stubs that throw). Without `export const dynamic = "force-dynamic"` Next tries to statically prerender them at build time, EXECUTES the stub, and the build fails — turning a structure check red for a logic-absent reason. `force-dynamic` makes them request-time (`ƒ`), so build compiles without executing the read. This is the UI analogue of "structure green, harness red".
3. **In-process cross-package test, the (B) + (b) payoff.** `dash_ac_001` drives the REAL read-API in-process (`services/api`'s `buildApp` + `app.inject`, backed by Postgres + Redis testcontainers — no api Docker image, the (A) toll avoided) by DYNAMIC import with a **non-literal specifier** (`const loadApi = (s) => import(s)`). The non-literal specifier is load-bearing: a literal `import("@cyberguard/api/...")` makes tsc typecheck api's NodeNext source under the dashboard's `isolatedModules` config and fails (`TS2748` ambient const enum from `@node-rs/argon2`). The non-literal yields `Promise<any>` → runtime-only, never compiled here (same principle as the (b) retiral's dynamic migration import). A green "harness sanity" check (real read-API → 200) proves the harness is sound, so the RED is unambiguously logic-absent.
4. **`check-dashboard` runs `next build` BEFORE `tsc`; `next-env.d.ts` is gitignored.** Next 15.5 regenerates `next-env.d.ts` with a `/// <reference path="./.next/types/routes.d.ts" />` line pointing into the gitignored `.next/`; committing it would break a typecheck that runs before a build (missing file). So `next-env.d.ts` is gitignored (create-next-app convention) and the CI job order is install → **build** → typecheck → lint → test, letting the build regenerate the Next types the typecheck then consumes.
5. **UI view types are decoupled from the server's read-models by design.** `dashboard/src/lib/api/types.ts` re-declares the read-API JSON shape rather than importing `services/api/src/read/types.ts`; the dashboard talks HTTP, so its contract is the wire shape, and `dash_ac_001` (against the real API) is what binds them — drift would surface there, not in a shared type.

RED state at the gate: `check-dashboard` red (5 failing dash_ac assertions on absent logic + 1 green harness-sanity guard); `check` (ingest) + `check-api` (read-API, 31) green; structure (`next build`/`tsc`/`biome`) green. Known CI debt co-located (Convention #13, two-commit SHA-placeholder), removed at the dashboard GREEN gate.

**GREEN (C closed).** The data-access layer (`getIncidents`/`getIncidentDetail`) and the presentational views (`IncidentsTable`, `IncidentDetailView`) replaced the stubs: all 6 dashboard tests green (3 data-access against the real read-API in-process + 2 render + the harness-sanity guard, intact). The auth→read→render chain works end to end (a valid `cgsess` → 200 + data; no/invalid session → real 401 → `unauthenticated` → the RSC `redirect("/login")`; a detail 404 → `not_found` → `notFound()`). `ReadResult` gained a `not_found` variant (additive, backward-compatible; the `dash_ac_001` `unauthenticated` assertions unchanged). Two small render-fidelity choices kept the committed RED assertions honest at GREEN: the MITRE technique is rendered once at the incident level (so `getByText(/T1059\.001/)` matches uniquely), and a plain `<a>` (not `next/link`) is used so the presentational components render standalone under jsdom without the App Router context. The dashboard impl touched only `dashboard/` — `services/api` and `services/ingest` were consumed, never modified (verified by diff). Known CI debt back to ZERO in the same SHA. Slice C (read-API + minimal SOC dashboard, SPEC-009) is delivered; the `dashboard/` dev-compose wiring (`+ .env.example`) is a named follow-up chore (mirroring how `services/api` was wired), deferred to its own SHA.

### Session 19 — procedural notes (convention candidates)

Three process lessons from the C arc, recorded for promotion review at a future gate. The full canonical close is in [handoff-session-19.md](handoff-session-19.md).

1. **A green AC inside a RED suite deserves an audit of WHAT it asserts, not just that it passes.** A *spurious-green* (a test that passes because its setup silently no-ops — e.g. an assertion that never runs, or runs against an empty fixture) is the opposite of a legitimate *green-guard* (one that passes *because* it proves live infrastructure). The dashboard RED gate's "harness sanity" guard was written deliberately as the latter: it asserts a real `200` + non-empty `items` from the in-process read-API, so its green proves testcontainers + `buildApp`/`app.inject` + the cross-package import are alive — which is what makes the sibling RED failures unambiguously logic-absent rather than setup-broken. When a test is green during a RED phase, confirm it is a guard, not a no-op.
2. **Adding a NOT NULL column / changing a schema requires auditing ALL writers** (production + test fixtures) — reconfirmed. The (b) retiral repointed the read-API harness from a column-subset DDL mirror to ingest's REAL schema; that real schema's NOT NULL/CHECK constraints (`cg_detection_source`, `source_events`, `dedup_key`, `heuristic_score`, `grouping_key`, `window_start`, `agents.pubkey`/`cert_pem`/`expires_at`) forced every seed helper to construct production-faithful rows. The constraint doing its job *is* the signal; the fix is to satisfy it, never to weaken it (Convention #12). First recorded Session 18 (`68c95f8`).
3. **Stop-and-ask at architecture forks worked — three catches that prevented disguised RED-by-setup.** The read-API materialisation fork (a / a' ClickHouse-coupled / (c) DDL mirror) and the dashboard-test fork (Docker-image (A) vs pnpm-workspace (B)) were each PARA'd to Manuel rather than improvised past. The workspace decision (B) then unlocked both the faithful (b) retiral and in-process UI testing. Stopping at the fork — not coding through it to a green that hides a setup compromise — is what kept all three RED gates (auth, read-API, dashboard) honest.
