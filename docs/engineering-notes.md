# Engineering notes

Session-level engineering lessons. Not ADRs (no architectural decision), not SPECs (no feature). Working memory: patterns that accelerate similar decisions later. If a pattern recurs, promote it to an ADR.

## Session 5 (2026-05-20)

- **Test API exposure trade-off.** If a test requires exposing something dubious to the public API (e.g. internal logger primitives for AC-009 testability), restructure the test rather than the API. Bloating public surface for test convenience accumulates faster than expected.
- **chrono dependency trade-off.** `chrono` is heavy but the alternative (manual ISO 8601 with days-from-epoch) was 30+ lines and edge-case-prone. For RFC 3339 timestamps in the agent, `chrono` is the right call.

## Session 10 (2026-05-23)

- **Follow-ups are co-located with the document that generates them.** A spike's follow-ups live at the bottom of the spike note; an ADR's follow-ups live at the bottom of the ADR; an amendment's follow-ups live with the amendment. No central `docs/follow-ups.md` index is created proactively — that would be premature abstraction. If dispersion later makes auditing hard, an index gets created **then**, populated from the existing in-place sections. The rationale is that a follow-up is most useful when read next to the evidence that justified it; separating them loses signal.
- **ADR Deciders field — three-role convention formalised.** Every ADR header uses `- Deciders: Manuel (project owner), Claude (architecture advisor), Claude Code (implementation)` verbatim. ADRs 0001–0008 already use this form by consistent copy; this note promotes it from accidental pattern to explicit precedent so future ADRs adopt it by reference, not by copy.
- **Cross-reference convention — provenance points to the cause, not the effect.** When an amendment closes a prior drift, the rewrite-side bullet cites the drift's **original declaration** (the cause), not the amendment (the effect). A future reader follows the arrow to the cause, sees the drift, and finds the amendment as the closure; reverse arrows force backwards reconstruction. Adopted while writing ADR-0004's 2026-05-23 amendment part (b), which closed SPEC-003 §Drift D3 in ADR-0004's prose.
- **Internal cross-check for multi-mention claims.** Any document where a load-bearing claim appears in more than one place (e.g. ClickHouse partitioning summarised in Context AND specified in Decision) needs an internal-consistency pass before submission, not only when amending a ratified file. Surfaced while reviewing the ADR-0009 draft, where a Context-section paraphrase of ADR-0003's partitioning contradicted the Decision-section spec.
- **Audit cross-references on reserved-ADR repurposing.** When a reserved ADR number is ratified for a new topic (e.g. ADR-0008 was reserved for "contract generation tooling" and ratified as "ETW crate selection"), sweep the repo for cross-references that were written under the old reservation. Lexical audit scoped to an amendment's immediate terms cannot catch these — they need a separate sweep. Surfaced when ADR-0004's §Consequences > Neutral still attributed API-versioning to "ADR-0008 (contract generation tooling)" after ADR-0008's ratification this session.
- **Dependency-graph edge convention — "amends in part" vs "supersedes".** When an ADR amends another ADR in-place (via `## Amendment <date>:` section, target ADR stays `Accepted`), the dependency-graph edge in [docs/adr/README.md](adr/README.md) is labelled "amends in part," not "supersedes." Supersession is reserved for cases where the target ADR's status flips to `Superseded`. The distinction matters: "amends in part" preserves the target's accepted-status authority; "supersedes" retires it. Adopted with ADR-0009's edge to ADR-0004.
- **Dep-graph edges capture constraint-bearing relationships only.** Non-constraining but topic-relevant relationships live as bullets in the ADR (typically §Consequences > Neutral or an inline cross-reference), not as edges. Do not invent edges to document absences — an edge labelled "non-constraining cross-reference" is incoherent. Absence of edge **plus** an explicit bullet explaining the absence is more informative than an edge with an apologetic annotation. Adopted while drafting ADR-0010's relationship to ADR-0004 (DPAPI privilege-orthogonality: topic-relevant, non-constraining; documented as a Neutral bullet, no edge).
- **Spike notes are point-in-time records, not living documents.** Their text is anchored to the date in the filename; forward-references that become stale after the spike's date are NOT edited retroactively. Erratas (typos, factual misstatements about the moment of writing) are editable; semantic updates (forward-pointers fulfilled, decisions later changed) are not — those would be documentary revisionism. This distinguishes spike notes from ADRs in the doc taxonomy: ADRs speak in the present (amended in-place when their content changes); spike notes speak in a date-anchored past. Adopted when ADR-0010's ratification surfaced "ADR-0010 (forthcoming)" in [docs/spikes/2026-05-23-etw-process-events.md](spikes/2026-05-23-etw-process-events.md) — kept unchanged because the statement was true on 2026-05-23 when the spike was written.
- **Bidirectional cross-reference audit on amendment.** When document X is amended, audit cross-references **to** X from other documents in the same session — they may need provenance updates. This is the inverse direction of the "provenance to cause" and "audit on reserved-ADR repurposing" conventions, which cover cross-references **from** the amended document. Together, the three conventions form a bidirectional matrix: amendments propagate both within X (handled by the in-document lexical audit per the Session 9 lesson) and across documents that cite X (handled by this convention). Adopted when SPEC-003's amendment audit surfaced three provenance citations to ADR-0004 sections that this session's ADR-0004 amendment had already changed.

  **Procedural footnote.** Cross-references detected **during drafting** (not during the formal audit pass) should be surfaced explicitly in the draft for chat approval before being silently applied, even when the correction is factually obvious. The audit pass is the moment of accountable scope-setting; corrections found later need an explicit retroactive scope-extension, not silent inclusion. Adopted after a *"Go ingest service"* → *"TypeScript ingest service"* correction was found during SPEC-003's amendment drafting (Session 10) without surfacing in the audit pass — the correction was kept (documentary integrity beats procedural integrity when the substance is non-controversial) and part (c) was extended in chat-approved form, but the procedural pattern is recorded so future audits surface the find at audit-time, not drafting-time.

## Session 11 (2026-05-23)

- **Convention #5 extension: the cross-reference sweep on reserved-ADR repurposing is REPO-WIDE, performed in the commit that ratifies the new ADR meaning.** Session 10's ratification of ADR-0008 (originally reserved for "contract generation tooling," ratified as "ETW crate selection" at `265b771`) swept ADR-0004 for stale references but did not extend the sweep repo-wide. Session 11's audit of ADR-0006 prior to introducing class 1007 surfaced two missed instances: ADR-0006 line 133 (the §Compliance bullet attributing contract-generation tooling to ADR-0008, fixed at `a52a841`) and ADR-0005 line 159 (the "Future ADRs (notably `ADR-0007` — Normalize before correlate)" framing, which combined ADR-0006's reserved-when-cited status with ADR-0007's separate Session 8 repurposing as "Ingest language — TypeScript for MVP", ratified at `0f11424`). This is an **extension to** Convention #5 from Session 10's engineering-notes entry, not a new tenth convention: the original Convention #5 ("Audit cross-references on reserved-ADR repurposing") stands; the procedural footnote here is that the audit is repo-wide and performed at ratification time, not scoped to a single document being amended. Adopted while closing the procedural debt surfaced by Phase 3.1.1's audit.
- **Operational: poll CI workflows by full SHA, not short SHA.** The GitHub Actions REST API's `head_sha` query parameter (used by the fallback polling per [CLAUDE.md](../CLAUDE.md) §CI monitoring) returns no matching runs for a short SHA — the API requires the full hex. Phase 3.1.A's polling for SHA `a52a841` returned `NO_RUNS_YET` for ~30 consecutive polls before the script exited the loop without ever finding a run; Phase 3.1.B's polling for SHA `e6d5b69226080bc6d58a61d7fd0e963e1b808e71` (constructed via `git rev-parse HEAD`) reached terminal state on poll 1. Future agents: always pipe through `git rev-parse HEAD` before constructing the REST API URL.
